## Findings

- **[M] [fail-open/UX] service/TunnelController.kt:200-209,225-238, service/TailcatVpnService.kt:303-322 — Mid-session failure tears the VPN down silently, clears `vpnWanted`, and never retries**
  On any `PumpFailed`, `TransportLost`, 3x `HealthStale`, or a *single* `getStats()` exception (`MAX_TELEMETRY_FAILURES = 1`), the poll loop calls `reportError` (in-app flows only) and then `stopTunnel()`. That sets `vpnWanted=false`, and `shutdown()` closes the TUN and calls `stopForeground(STOP_FOREGROUND_REMOVE)`. No notification says the VPN dropped: the ongoing notification just disappears and the error is visible only if the user opens the app. Without lockdown, all traffic goes direct from that moment, and nothing restores it. `vpnWanted=false` also stops `restoreIfWanted` from retrying on the next resume or process start.
  Scenario: a transient pump error or one JNI hiccup while the phone is in a pocket leaves the user unprotected for hours with no signal.
  Fix: post a high-visibility "VPN disconnected: <cause>" notification with a Reconnect action. Keep `vpnWanted=true` for engine-initiated failures and retry with backoff (re-prepare) while holding the routed TUN in fail-closed mode. Raise `MAX_TELEMETRY_FAILURES` to ~3. Effort M.
  (Unverified: whether Android re-launches an always-on, non-lockdown VPN that stopped itself. From AOSP `Vpn.java`, I believe it doesn't until the next boot, user switch, or package update.)
- **[M] [state-machine/availability] service/EngineHealth.kt:23-24,57-59, service/TunnelController.kt:211-217 vs core-engine/bridge.go:790-818,890-909 — Gateway loss is never detected: `TransportLost` can't fire, and a dead gateway shows DEGRADED forever**
  Go's `healthUnixSec` is a pumps-alive heartbeat (`rateCalcLoop` refreshes it every 1 s whether or not the gateway answers). `transport` starts as `DERP_RELAY`/`DIRECT_P2P` from `Prepare` and is only ever overwritten with those two values after a successful `DiscoPing`. A failed DiscoPing only sets `discoStale`. So in `RUNNING`, Go never reports `UNKNOWN`/`DISCONNECTED` (except in a sub-millisecond `bridge.closed` race), and `EngineHealth.TransportLost` is effectively dead code. When the gateway dies or the path breaks after a roam (no Magicsock rebind, see baseline "Network-change injection is dead code"), Kotlin shows `DEGRADED` indefinitely. Traffic is blackholed (fail-closed, not a leak), with no teardown, no re-prepare and no user prompt beyond "Tunnel Degraded".
  Fix: in Go, publish `lastDiscoOkUnix`/`pingFails`. In Kotlin, treat "disco stale for > N s (e.g. 30-60 s)" as a reconnect trigger: re-`prepare` behind the routed TUN, or tear down with a notification. Delete `TransportLost`, or make Go actually emit it. Effort M.
- **[L] [broken status/dead code] service/LockdownProbe.kt:31-54,62-69, ui/screens/settings/SettingsScreen.kt:220-232 — The lockdown status probe cannot read its settings on API 35 / target 35; `lockdownSatisfied` is dead code** *(confirmed live)*
  On the API 35 emulator (app `targetSdk=35`), Settings > "Always-on & kill switch" shows **"Status: Lockdown settings could not be read on this device."** The only path to that text is the `SecurityException` catch, so `Settings.Secure.getString("always_on_vpn_app")` is rejected for this app. These are `@hide` keys, and from Android 12 SettingsProvider enforces `@Readable` (with an optional `maxTargetSdk`) for third-party callers. The KDoc's premise ("prefer that signal ... observable before establish") is therefore false on current targets, so the only lockdown indicator the app offers never works on current Android. That matters because the baseline treats lockdown as the user's main protection. `lockdownSatisfied()` is used only by `LockdownProbeTest`. The Settings text "Recommended on Android 10+" is also off: "Block connections without VPN" exists from Android 8.0, and `LOCKDOWN_REQUIRED_API=29` only reflects when `VpnService.isAlwaysOn()/isLockdownEnabled()` were added.
  Fix: while the service runs, read `isAlwaysOn()`/`isLockdownEnabled()` (API 29+) and publish them through `TunnelController` (for example on each `onStartCommand`/`onEngineConnected`). When not running, show "unknown: open Android VPN settings". Delete the Settings.Secure path and `lockdownSatisfied`, and fix the API wording. Effort S.
  (Unverified: whether the keys are readable at target ≤ 34 on API 31–34. That doesn't change the fix.)
- **[L] [state-machine] service/TunnelController.kt:109-124, ui/MainActivity.kt:19,48 vs service/TailcatVpnService.kt:157-183 — `resyncFromEngine` can declare CONNECTED during the warm (host-routes-only) phase and start a second poll loop**
  `resyncFromEngine()` runs on every `onCreate`/`onResume`. It skips only when the state is `CONNECTED`, so during `CONNECTING` it polls native. After the warm `attachLive`, native is `RUNNING` with fresh health and a transport, which satisfies `shouldConnect`. `onEngineConnected` then sets `CONNECTED` and starts the poll loop while only `100.64.0.2/32` and `fd7a:…::2/128` are routed, so device traffic still goes direct. That breaks invariant 3. The window is `protectOpenTransportSockets` + `detachTun` + routed establish: ~0.45 s on the emulator, and 3 s or more when detach hits the baseline blocked-reader stall. Any resume (screen on, app switch) inside that window triggers it. If the stall reaches 3 polls, the resync-started loop sees `PREPARED` (health 0) three times and calls `stopTunnel()`, which aborts the connect with a false "VPN data plane failed: no fresh engine health … (state PREPARED)". The same function also flips `DEGRADED`/`RECONNECTING` back to `CONNECTED` on every resume, for up to 1 s, until the next poll.
  Fix: only the service may promote to CONNECTED. Have the service publish a `startupPhase`/session token, and have `resyncFromEngine` act only when no start is in flight (for example `state == DISCONNECTED && vpnWanted`). Effort S.
- **[L] [lifecycle] service/TailcatVpnService.kt:36-39,113-146,185-195 — Disconnect/revoke during startup: spurious error banner, and a small window that leaks a prepared native session**
  (a) STOP or revoke while `prepare()` is blocked: `shutdown()` → native `stop()` cancels the session, and `prepare` throws `IllegalStateException("gateway handshake failed: context canceled")`. That is not a `CancellationException`, so the generic catch runs `onVpnStartFailed(...)`, and the user who tapped Disconnect sees a red "gateway handshake failed: context canceled" error.
  (b) STOP arriving after `startJob` launched but before Go `Prepare` publishes its session (DNS validation, `updateNetworkState`, `setSocketProtector` JNI): `shutdown()`'s native `stop()` sees `STOPPED` and returns. `prepare` then completes a full gateway handshake. `ensureActive()` throws, and the catch calls `shutdown()`, which is a no-op because the CAS already fired. The Go session stays `PREPARED` with a live Magicsock/DERP client (sockets, goroutines, keepalives, battery) until the next connect or process death.
  Fix: `checkNotShuttingDown()` immediately before `prepare`. In both catch blocks call `tunnelEngine.stop()` unconditionally (it is idempotent). Treat any failure while `shuttingDown` is set as a user cancel (no error). Effort S.
- **[L] [ANR/main-thread JNI] EXTENDS: reviewer 1 "`Stop()` has no overall bound … main-thread `onDestroy`" — `rejectStart()` is the more reachable main-thread path**
  `onStartCommand` (main thread) → `rejectStart()` → `shutdown()` runs synchronously, so native `stop()` (≥3 s with the blocked TUN reader, see baseline and R1) blocks the UI thread. With the baseline ordering bug (validation before the running guard), this is exactly what happens when a redundant start intent arrives during a live session while the network is briefly unvalidated: the session is torn down *and* the main thread freezes for 3–6 s. `rejectStart` also calls `startForeground(..., SHORT_SERVICE)`, which demotes the running `systemExempted` FGS to `shortService` for that window. Fix: move the running guard first (baseline), and always run `shutdown()` on `serviceScope`. Only `stopForeground`/`stopSelf` need the main thread. Effort S.

- **[L] [race/stale state] service/TunnelController.kt:61-65, service/TailcatVpnService.kt:126-133,179,235 — Network-state pushes to Go are unordered, and startup re-pushes a stale snapshot**
  Each NetworkCallback event launches its own `scope.launch(Dispatchers.IO) { updateNetworkState(json) }`. A Wi-Fi loss produces a burst (`onLost`, `onCapabilitiesChanged`, `onLinkPropertiesChanged`) that can run on different IO threads in any order, and `UpdateNetworkState` is last-writer-wins (`customIfs`/`customDNSList` replaced wholesale). Go can therefore keep the *older* interface/DNS set until the next event. Separately, `establishAndStartEngine` captures `networkState` once, before a `prepare` that can take up to ~20 s, and `attachLive` sends that same snapshot again after both the warm and routed attach. Any roam during connect is overwritten with the pre-roam interfaces/DNS. Impact today is limited because Go uses this only for its own resolver (DERP hostnames, `tailcat.dev` map) and the netmon interface getter (`activeMonitor` is nil). But it can leave DERP re-resolution pointing at a dead network's DNS server after a roam.
  Fix: send updates through a single-threaded/conflated channel (`Channel(CONFLATED)` consumer or `limitedParallelism(1)` + latest-wins), and in `attachLive` rebuild the JSON from `networkMonitor.getNetworkStateJSON()` plus the profile fields instead of reusing the startup snapshot. Effort S.
- **[L] [correctness/thread-safety] core/NetworkMonitor.kt:39-40,77-89,105-135,150-161 — Network JSON merges every INTERNET network in arbitrary order; monitor state is written from two threads unsynchronized**
  `registerNetworkCallback(INTERNET)` tracks *all* matching networks, not the default one. On most phones the cellular network stays up in the background while Wi-Fi is default (the API 35 emulator has `WIFI wlan0` and `MOBILE eth0` both CONNECTED right now). `getNetworkStateJSON` puts both networks' interfaces and DNS servers into one list, in `ConcurrentHashMap` iteration order. Go's resolver uses only `dnsList[0]` (reviewer 1, L "never fails over"). So whether DERP hostname resolution uses the default network's resolver or a background cellular resolver (often a carrier-private address unreachable over Wi-Fi) is effectively random. `isOnline`, `networkType` and `gateways` are sent but never read by Go. On threading: `init` registers the callback (events start on `OpenTailcat-NetworkMonitor`) and *then* runs `allNetworks` + `updateNetworkStatus()` on the main thread. `lastNetworkStateJson` and `onNetworkStateChangedListener` are plain fields shared across both threads, so a change can be dropped or delivered twice, and the listener is installed only after events may already have fired. The `filterNot(TRANSPORT_VPN)` checks are redundant because `NetworkRequest.Builder()` adds `NOT_VPN` by default.
  Fix: track the default network (`registerDefaultNetworkCallback`, API 26+ OK) for DNS/interfaces, and send its DNS first. Run the initial snapshot on `callbackHandler` (post it) so all state is confined to one thread. Pass the listener in the constructor (or mark it `@Volatile`). Drop the unused JSON fields. Effort S.
Progress: finished core/NetworkMonitor.kt
- **[M] [fail-open/availability] EXTENDS: baseline H "Always-on start is rejected before the network validates" — every *handshake* failure also gives up permanently, even on a validated network**
  `establishAndStartEngine`'s generic catch (`TailcatVpnService.kt:189-195`) → `onVpnStartFailed` → `vpnWanted=false` → `shutdown()`/`stopSelf()`. Nothing re-arms a start: sticky restart doesn't apply after `stopSelf`, and `restoreIfWanted` sees `vpnWanted=false`. So a single `Prepare` failure ends the always-on session: the 10 s Ping timeout at boot while DERP DNS or the gateway isn't reachable yet, a brief gateway restart, or a Wi-Fi association that validates a few seconds before DHCP DNS works. The validation gate isn't involved. Result: lockdown users stay offline until they open the app, and non-lockdown users go direct with only an in-app banner. Fix (together with the baseline fix): for service-initiated or always-on starts, keep `vpnWanted`, retry `prepare` with capped exponential backoff (e.g. 2 s → 60 s) while `startForeground` shows "Waiting for gateway…", and give up only on non-retryable errors (invalid/expired token, consent revoked). Effort M.
- **[L] [main-thread JNI/startup] TailcatApplication.kt:49, service/TunnelController.kt:93-101,126-131, service/TunnelEngine.kt:100-108,214-253 — The 19.5 MB Go library is loaded and initialised on the main thread inside `Application.onCreate`**
  `restoreIfWanted()` evaluates `validateStartRequest()` eagerly as an argument to `VpnRestore.shouldRestore`, *before* `vpnWanted` is checked. With a valid token on a validated network, that reaches `tunnelEngine.availability` (a `lazy`), which does `Class.forName` → `System.loadLibrary("gojni")` (arm64 `libgojni.so` = 19,513,248 bytes), runs Go runtime and package `init` (tailscale/gVisor globals, `http.DefaultTransport` swap, netmon getter), and calls `getCapabilitiesJSON`. This happens on every process start, including when the system starts the process only to launch the always-on service, and even when the user never wanted a VPN. Otherwise the first touch lands on the main thread later (`HomeViewModel.canStartTunnel` on tap, `SettingsScreen` composition). That is cold-start jank, and on low-end devices part of the boot-time always-on start latency. (Unverified: exact cost; measure with a Perfetto cold-start trace.)
  Fix: check `vpnWanted` before validating (`if (!preferences.vpnWanted) return false`), and warm `availability` on `Dispatchers.IO` at startup, exposing it as a `StateFlow`. Effort S.
- **[L] [notification/hardening+battery] service/VpnNotificationManager.kt:33-91, service/TailcatVpnService.kt:281-298 — Unauthenticated lock-screen "Disconnect", and the notification is rebuilt and re-posted every second**
  (a) The Disconnect action has no `setAuthenticationRequired(true)` (API 31+). With the default "show all notification content" lock-screen setting, `VISIBILITY_PRIVATE` shows the full notification including the action, so anyone holding the locked phone can switch the VPN off. That sends traffic direct without lockdown, and it also clears `vpnWanted`. (b) `networkMetrics` emits on every 1 s poll (`healthUnixSec`/rates always change), and each emission creates two `PendingIntent`s (AMS binder calls) plus a `notify()` that SystemUI re-inflates. That runs for the whole session, screen off included. Content is otherwise fine: no IPs, only profile name, transport, RTT and rates. The only oddity is "DERP Relay #0"/"DERP 0" when the token has no `i`, because Go always emits `derpRegionId` and that is the token's configured region, not a measured relay.
  Fix: `NotificationCompat.Action.Builder(...).setAuthenticationRequired(true)`. Build the `PendingIntent`s once. Throttle notification updates (e.g. `sample(5_000)` or only on state/transport change, and pause while `PowerManager.isInteractive` is false). Treat `derpRegionId == 0` as null. Effort S.

- **[L] [split-tunnel scope] service/SplitTunnelExclusions.kt:19-24, service/TailcatVpnService.kt:269-271, ui/screens/settings/SettingsScreen.kt:117-141 — Excluding one package silently excludes every package sharing its UID (including system UIDs)**
  `addDisallowedApplication(pkg)` works on the package's UID. The picker lists every installed package (`QUERY_ALL_PACKAGES`, system packages included) with no UID information. Checking a `sharedUserId` member therefore removes *all* packages with that UID from the VPN: "Android System"/`com.android.settings`/other `android.uid.system` packages (UID 1000 = system_server traffic), `com.android.phone` (UID 1001), or GMS/GSF. The user thinks they excluded one app. Only the own package is filtered out. `validPackages` also accepts system packages without warning.
  Fix: resolve `ApplicationInfo.uid`, group or dedupe by UID in the picker ("also excludes: …"), and hide or warn on UID < 10000 (`Process.FIRST_APPLICATION_UID`). Effort S.
- **[L] [state-machine/UX] service/TunnelController.kt:167-175, service/TailcatVpnService.kt:303-327 — No DISCONNECTING state: the UI and notification keep saying "Connected" for the whole native stop**
  `stopTunnel()` only cancels polling and sends `ACTION_STOP`. `_tunnelState` stays `CONNECTED` (metrics frozen) until `shutdown()` finishes: TUN close → native `stop()` (2–3 s measured in the baseline live run, 3–6 s per reviewer 1) → a main-thread post of `onVpnStopped`. During that window the TUN is already closed, and the device is blackholed and then direct (without lockdown), while the app and the ongoing notification still show "Connected (<profile>)". A second tap just sends another STOP. The same applies to poll-initiated teardowns. Fix: add `TunnelState.DISCONNECTING`, set it synchronously in `stopTunnel()`/`shutdown()` before closing the TUN, and update the notification immediately. Effort S.

- **[M] [tests] app/src/test/**, app/src/androidTest/** — The critical Kotlin state machine has no tests; several existing tests are tautological or lock in fail-open behavior**
  What is real: `EngineHealthTest`, the `NetworkMetrics` parsing/freshness cases in `TunnelEngineTest`, `VpnRestoreTest`, `SplitTunnelExclusionsTest`, `TransportSocketProtectTest` (pure helpers, meaningful), and `VpnStartupInstrumentedTest`, which is a real device test of consent-missing and synthetic-token failure (no routes, service stopped, `vpnWanted` cleared).
  Weak: `NetworkMonitorTest` parses a hand-written JSON literal with `org.json` and never touches `NetworkMonitor`. `StaleExitIpFixTest` re-implements the `TelemetryCard` expression inline ("Simulate TelemetryCard logic") instead of testing it. `LockdownProbeTest` injects fake readers, so it passes while the probe is broken on API 35 (above). `TunnelEngineTest.testStopLifecycleIdempotent`/`testDetachTunSafeWhenUnavailable`/`testDisarmPumpsSafeWhenUnavailable` assert that `stop`/`detachTun`/`disarmPumps` silently do nothing when the engine class is missing, which is exactly the fail-open the baseline flags. ## Overall assessment (written by the main session; the reviewer finished every file but hit the usage limit before this section)
