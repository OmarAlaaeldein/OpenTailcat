### core/update + SettingsViewModel (updater)

- **[M] [updater/supply-chain] core/update/ApkInstaller.kt:45-49,69-75 + ui/screens/settings/SettingsViewModel.kt:85-90 — EXTENDS: signatureMismatchReason — the pre-install check blocks the recommended v3 key rotation**
  `signerDigests` compares only `signingInfo.apkContentsSigners` (current signer) of the downloaded APK with the installed app's current signer. An APK signed with a v3 rotation lineage (debug -> release, which is baseline P0 #1) has `apkContentsSigners = [release]`, while the installed app has `[debug]`. The intersection is empty, so the VM deletes the file and shows "APK is not signed with this app's key (install would fail)", even though PackageManager would accept the rotated APK.
  Scenario: the developer does the recommended rotation. Every existing user's in-app update fails, and they have to sideload manually or stay on the debug-signed build.
  Fix: when `!signingInfo.hasMultipleSigners()`, accept the APK if any cert in the archive's `signingCertificateHistory` matches the installed signer. Also pin the expected release-cert digest here (see baseline P0 #2). Effort S.
- **[L] [threading] ui/screens/settings/SettingsViewModel.kt:72,82-86 — APK archive parsing and signature verification run on the main thread**
  `viewModelScope` defaults to `Dispatchers.Main.immediate`. After `download()` returns, `signatureMismatchReason` calls `getPackageArchiveInfo(..., GET_SIGNING_CERTIFICATES)` on Main. That call parses the whole APK (the local debug outputs are 37-38 MB) and verifies its signature.
  Scenario: a visible UI freeze when the download finishes on a slow device. ANR risk grows with APK size.
  Fix: wrap the call in `withContext(Dispatchers.IO)`. Effort S. (unverified: how long it takes on-device; that depends on how much of the full v2/v3 digest check `getPackageArchiveInfo` runs on each API level)
- **[L] [lifecycle] ui/screens/settings/SettingsViewModel.kt:63,85-86,102-124 — ViewModel coroutine captures the Activity Context**
  `downloadUpdate(context)` holds the caller's Context in a coroutine that can run for minutes (30 s read timeout per chunk, large APK). After a rotation or dark-mode change, the destroyed Activity stays in memory until the download ends, and `packageManager` is then called through it. `openInstall` also starts activities with whatever Context it is given.
  Fix: use `app.applicationContext` (the VM already holds `TailcatApplication.instance`) for package-manager work. Keep the Activity only for the `startActivity` calls made directly from the click handler. Effort S.
- **[L] [updater] core/update/GitHubReleaseClient.kt:15-16 — `/releases/latest` ignores pre-releases, so baseline P0 #1 ("mark GitHub releases as pre-release") silently disables the updater**
  GitHub's `releases/latest` returns only the newest non-draft, non-prerelease release. Once builds are published as pre-releases, the check returns 404, shown as "No published release found", or keeps pointing at the last full release, which would be the debug-signed 1.4.0.
  Fix: decide on a policy. Either list `/releases?per_page=10` and take the newest one with a matching signed checksum (opt-in to pre-releases), or keep full releases once the signing fix lands. Document the choice together with P0 #1. Effort S.
- **[L] [updater/defense-in-depth] core/update/ApkDownloader.kt:39-40 — Download path built from the server-supplied asset name**
  `File(File(cacheDir,"updates"), asset.name)` takes `name` straight from the release JSON. `apkAssetForAbi`'s loose fallback accepts any `*.apk` containing the ABI string, so a name such as `../files/x-arm64-v8a.apk` would write outside `cache/updates` (inside app-private storage) before any signature check runs. GitHub sanitizes uploaded asset names today, so this is not exploitable through GitHub itself; it matters if the source changes or the response is ever not from GitHub.
  Fix: write to a fixed name (`update-<version>.apk`) or reject names containing `/`, `\`, or `..`. Effort S.
Progress: finished core/update/*.kt (ApkDownloader, ApkInstaller, GitHubReleaseClient, ReleaseModels) and SettingsViewModel.kt. PinnedHttps.kt: nothing new beyond the baseline TLS-pin findings.

### Settings screen

- **[L] [UI bug] ui/screens/settings/SettingsScreen.kt:581 + SettingsViewModel.kt:143-148 — "Check again" doesn't check**
  In the `UpToDate` state, the "Check again" button calls `resetUpdate()`, which only sets `Idle`. The user sees the "Check for update" button again and has to tap a second time. Fix: call `checkForUpdate()`. Effort S.
- **[L] [UI bug] core/update/ReleaseModels.kt:49-52 + SettingsScreen.kt:589,595-598 — A JSON `null` release body or name is shown as the literal text "null"**
  Android's `JSONObject.optString(name)` returns `"null"` for JSON null (`JSON.toString(JSONObject.NULL)`). GitHub returns `"body": null` for releases published without notes. `notes.isNotBlank()` is then true, and the update card shows "null" under "Update available". Fix: `if (root.isNull("body")) "" else root.optString("body")` (same for `name`). Effort S.
- **[L] [UI honesty] ui/screens/settings/SettingsScreen.kt:459-481 — The "exclusions changed while the tunnel is up" warning compares against the wrong baseline and resets on scroll**
  `originalExclusions = remember { store.splitTunnelExcludedApps }` sits inside a `LazyColumn` `item {}`. It captures the list when the Apps tab is composed, not the list the running session actually applied. It is re-captured whenever the header item scrolls off-screen and back, or the tab or screen is re-entered. After one scroll or a tab switch, the yellow "Disconnect and Connect again for it to apply" warning disappears, although the running tunnel still uses the old exclusions (the neutral text below it is still shown).
  Fix: have the service publish the exclusion set it applied (e.g. `TunnelController.appliedExclusions`) and compare against that, hoisted out of the lazy item. Effort S.

### Data layer

- **[L] [data loss/privacy] data/ProfileRepository.kt:113-126 + ui/screens/home/HomeScreen.kt:485-490 — Re-pairing a gateway silently resets its name, DNS policy and MTU**
  `addOrUpdateFromToken` matches an existing profile by server key but rebuilds every field from the dialog. That means `name.ifBlank { "Gateway-xxxxxx" }`, the dialog DNS (defaults to `store.defaultDns`), the dialog policy (defaults to `PROFILE_RESOLVER`) and the current `defaultMtu`. Scenario: the user refreshes an expiring token for the same gateway. A profile that had `FORCED_RESOLVER` + 9.9.9.9 quietly goes back to profile-resolver DNS, and its custom name is lost. Nothing in the UI says an existing profile was overwritten.
  Fix: when `existing != null`, keep its name/DNS/policy/MTU unless the user changed them. Pre-fill the dialog from the existing profile once the key is recognized, or show "Updates existing profile X". Effort S.
- **[L] [dead code] core/model/GatewayProfile.kt:14, data/ProfileRepository.kt:50,64,124,173-181 — `isDefault` is half-implemented**
  It is set only on the first profile and read only as a load fallback when `activeProfileId` is missing. `deleteProfile` never moves it, and no UI sets or shows it. Delete it (the active id already covers this), or implement it properly. Effort S.

### core/dns, core/ip, core/metrics

- **[L] [privacy/latent] core/dns/DnsValidator.kt:139-143 — "IPv6" validation uses `InetAddress.getByName`, which does a DNS lookup for non-literals**
  Any input with a `:` and no `.` (e.g. `router:1`, `cafe:babe`, `zz::1`) goes to `InetAddress.getByName`. For a non-numeric string, libcore falls through to `lookupHostByName`, which is a real resolver query. Today every user-typed input is validated on the main thread (SettingsScreen:311/316/359, HomeScreen:497, ProfileRepository), so StrictMode's default `NetworkOnMainThreadException` aborts the lookup and the `runCatching` turns it into Invalid. So no query goes out, but only by accident. Moving validation to a ViewModel on `Dispatchers.Default`/IO would send the typed string to the physical network's resolver. (`DnsValidatorTest` does not currently feed a colon-bearing non-literal, so the lookup path is untested.)
  Fix: use a literal-only parser (`InetAddresses.isNumericAddress`/`parseNumericAddress` on API 29+, or a small hextet parser for API 26-28). Effort S.
Progress: finished core/dns/DnsValidator.kt, core/ip/IpAuditor.kt (only the baseline's stale app-UID KDoc), core/metrics/TrafficFormat.kt (clean; `formatKbps` shows kilobits while the notification shows bytes/s, a cosmetic inconsistency)

### Home screen + TelemetryCard

- **[M] [UI honesty / invariant 4] ui/screens/home/HomeScreen.kt:444, ui/screens/home/components/TelemetryCard.kt:149-167,209-223,307-311 — DEGRADED is labeled "RELAYING" and keeps showing the last transport and RTT as if they were live**
  `DEGRADED` is set only from `metrics.discoStale` (TunnelController.kt:212-216), meaning the last DiscoPing to the gateway failed. On failure Go keeps the previous `transport` and the previous RTT/jitter (bridge.go:798-805, 945-946). The UI then shows the status "DEGRADED • RELAYING" (suggests traffic is flowing over DERP), a badge that can still read "DIRECT P2P (…)" (which contradicts "relaying"), the RTT text "23 ms (±2)" from the last good sample (possibly minutes old), and a footnote "RTT stale (relay)". Reviewer 02 found a dead gateway sits in DEGRADED indefinitely, so this screen presents a dead or unreachable gateway as a working relay with a low latency.
  Fix: label it "DEGRADED • GATEWAY NOT RESPONDING". When `discoStale`, grey out or hide RTT and transport (or show "last reply Ns ago"; Go would need to export `lastDiscoOkUnix`). Drop "(relay)". Effort S.
- **[L] [UI honesty] ui/screens/home/components/TelemetryCard.kt:63 — EXTENDS: "Egress audit retries forever": the UI shows "Exit IP: Checking…" indefinitely and never shows `egressAuditError`**
  When the native audit keeps failing (the pinned leaf rotates on 2026-12-21, or the gateway filters 1.1.1.1:443), `tunnelEgressIp` stays null and the card says "Checking…" for the whole session. The error string Go already publishes (`egressAuditError`) appears only in the debug failure banner.
  Fix: after the first failed attempt (or N s), show "Exit IP: unavailable (<short cause>)". Effort S.
- **[L] [stale comment/duplication] ui/screens/home/components/TelemetryCard.kt:57-60,75-76,106,151-152 — Stale app-UID comment, hardcoded VPN addresses, dead `directEndpoint` branch**
  Line 75-76 repeats the false "The app UID bypasses the Android VPN" claim. This is another location for the baseline's stale-claim finding; the conclusion "never IpAuditor while connected" still holds, but for a different reason. Line 106 hardcodes "100.64.0.2 / fd7a:115c:a1e0::2" instead of `VpnInterfaceSpec.IPV4_ADDRESS/IPV6_ADDRESS`; they match today but will silently drift. Lines 151-152 render `DIRECT P2P ($ep)`, but Go never sets `directEndpoint` (baseline dead-field list), so that branch is dead. Fix: fix the comment, reference the constants, delete the branch or populate the field. Effort S.
- **[L] [privacy] ui/screens/home/HomeScreen.kt:545-560 — The token field lets the keyboard learn and suggest a credential**
  The token field (which can carry the WireGuard PSK `q` and is the gateway bearer credential) has no `keyboardOptions`. The IME treats it as normal text: personalized learning, suggestion strip, and cloud-synced dictionaries on some keyboards. `FLAG_SECURE` (baseline) covers screenshots, not the IME.
  Fix: `keyboardOptions = KeyboardOptions(keyboardType = KeyboardType.Password, autoCorrectEnabled = false)` (Password tells IMEs not to learn). Optionally a `PasswordVisualTransformation` with a reveal toggle. Effort S.
- **[L] [UX/data loss] ui/screens/home/HomeScreen.kt:394-407 + HomeViewModel.kt:109-115 — One tap on the trash icon deletes a profile (and its token) and stops the tunnel, with no confirmation or undo**
  The delete icon is the trailing icon of the same dropdown row the user taps to switch gateways. A mis-tap removes the only copy of the token, which may not be recoverable without the gateway operator, and disconnects if it was the active profile.
  Fix: a confirm dialog or an "Undo" snackbar before calling `profileRepository.deleteProfile`. Effort S.
- **[L] [state machine] ui/screens/home/HomeScreen.kt:139-145,147-158 + HomeViewModel.kt:66-79 — Async permission callbacks call `toggleVpn()`, which stops a tunnel that is already starting**
  After the notification-permission or VPN-consent activity returns, the callback calls `toggleVpn()`. That is a toggle, not an idempotent connect. Leaving the permission activity triggers `MainActivity.onResume -> resyncFromEngine -> restoreIfWanted`, which can start the tunnel when `vpnWanted` is still true. The callback then sees `CONNECTING` and stops it.
  Scenario: `vpnWanted=true`, but `restoreIfWanted -> startTunnel` returned early because `validateStartRequest` failed (offline). That early return does not clear `vpnWanted` (TunnelController.kt:139-143). Later the user taps Connect, grants POST_NOTIFICATIONS (API 33+) or VPN consent, and the resume-time restore starts the tunnel, which the callback then stops.
  Fix: add `HomeViewModel.connect()` that returns early unless `DISCONNECTED`, and use it from both callbacks. Effort S. (unverified on-device; narrow window)

### Speed test (engine, troubleshooter, report, screen)

- **[L] [UI honesty] ui/screens/speedtest/SpeedTestScreen.kt:160-164 + SpeedTestViewModel.kt:22 — EXTENDS: stale app-UID claim / speed-test "direct" labelling: the user-visible banner states the false claim, and it shows the wrong path before a test**
  The banner reads "Physical-network benchmark: the app UID bypasses the VPN, so this is the direct device path." It is keyed on `testState.viaGateway`, which defaults to `false`. On a CONNECTED phone the idle screen therefore says the test will use the direct path, then flips to "Gateway tunnel benchmark" once the test starts. In CONNECTING/RECONNECTING/DEGRADED the "physical" run actually goes into the routed TUN (the app is not excluded), so the claim is false in exactly the states where a user is troubleshooting.
  Fix: before a run, derive the label from live `tunnelState`. Either make the claim true (bind the physical run to the underlying network: `Network.openConnection`/`bindSocket` on the non-VPN `Network`, which the VPN owner can use), or reword it to "device network path (not via Tailcat DialTCP)". Effort S.
- **[L] [dead code / misleading findings] core/speedtest/SpeedTroubleshooter.kt:60,74,124-129 — Unreachable warning branch; stale-disco finding guesses "DERP fallback"; no finding for physical runs while a tunnel is half-up**
  `else if (viaGateway)` can never run, because `viaGateway` already satisfies the preceding `if (viaGateway || tunnelState == CONNECTED)`. So "Gateway benchmark requested while not CONNECTED" is dead. The `discoStale` finding says "(DERP fallback or no recent path probe)", but `discoStale` only means the last DiscoPing to the gateway failed; it is the same misreading as the DEGRADED/"RELAYING" label above. A physical-path run (`viaGateway=false`) during CONNECTING/RECONNECTING/DEGRADED produces no tunnel finding at all, even though its traffic went into the TUN.
  Fix: delete the dead branch or rewrite the condition to `!viaGateway && tunnelState != DISCONNECTED` -> "a tunnel was up but not CONNECTED; results reflect the VPN interface". Reword the stale finding to "gateway did not answer recent discovery pings". Effort S.
- **[L] [resource cleanup/cancellation] core/speedtest/SpeedTestEngine.kt:27,211-300 + SpeedTestViewModel.kt:20-31 — Cancelling a run doesn't stop it, and connections leak on failure**
  After the ping loop, the body of `runSpeedTest` has no suspension point or `ensureActive()`. `measureDownloadSpeed`/`measureUploadSpeed` are `suspend` in name only, and the gateway path makes blocking JNI calls (Go uses `context.Background()` with 8 s x5 ping, 20 s download, 20 s upload budgets, speedtest.go:30,52,73). A cancelled job (Activity finished, VM cleared mid-test) keeps downloading up to 5 s of a 25 MB body and uploading for 4 s, all unobserved. `stream.close()`/`conn.disconnect()` run only on the success path (lines 243-244, 287-291). A read timeout or HTTP error leaves the `HttpsURLConnection`/socket to GC. `currentStage`/`stageDetail` are mutable instance fields set from `Dispatchers.IO` without synchronization.
  Fix: call `ensureActive()` inside both loops, use `try/finally { disconnect() }`, keep stage and detail local to the run, and give the Go measurements a cancellable context (or at least a lower budget). Effort S.
- **[L] [measurement honesty] core/speedtest/SpeedTestEngine.kt:187-209,255-291 — EXTENDS: speed-test ping/upload inflation: the Kotlin physical path has the same flaws as Go**
  `measureSinglePing` times a whole HTTPS GET to 1.1.1.1: TCP + TLS handshake on at least the first sample, plus server time, then `disconnect()`. The tile says "PING (RTT)". Jitter is the mean |delta| between successive samples, so the cold-vs-warm first sample dominates it. Upload counts bytes as soon as they are written into the chunked stream (`totalBytesSent += buffer.size`, line 276), before acknowledgement, and the response code is read only after the 4 s window. Early samples reflect the socket send buffer, not the link.
  Fix: take one warm-up request and discard it, then measure small GETs on a kept-alive connection (or TCP connect time only). For upload, compute throughput from the server-acknowledged total (the `__up` response) or from time-to-response. Label the tile "HTTPS latency". Effort S-M.
- **[L] [privacy/sanitizer] core/speedtest/SpeedTroubleshooter.kt:22-34 — The clipboard-report IP sanitizer has gaps (checked by running the same regexes under java.util.regex, /tmp/otc-r3/San.java)**
  Redacted correctly: `203.0.113.5:443`, `[2606:4700:4700::1111]:443`, `::ffff:203.0.113.5` (embedded v4), `::ffff:cb00:7105`, full 8-hextet v6, `fe80::1%wlan0`.
  Leaks: `2001:db8::` and `2001:db8::/32` (a trailing `::` defeats the final `\b`) are **not redacted**. `x2001:db8::1` becomes `x2001[ip-redacted]` (the first hextet survives when a word character precedes it), and so does `fdead::beef:1` -> `fdead[ip-redacted]`. `ec2-203-0-113-5.compute.amazonaws.com` (IPs embedded in hostnames) and `ip_203.0.113.5` (underscore) are not redacted.
  Over-redacts: times such as `12:34:56`. Real exposure is low: current error sources mostly carry Cloudflare/gateway addresses, not the user's own, and no token reaches the report. It is a stated guarantee ("Never includes public exit/direct endpoints") that is not fully met.
  Fix: tokenize on non-`[0-9A-Fa-f:.]` boundaries and validate each candidate with a literal IP parser, redacting the whole token. Add a rule for `\d{1,3}(-\d{1,3}){3}` inside hostnames. Add these cases to `SpeedTroubleshooterTest`. Effort S.
