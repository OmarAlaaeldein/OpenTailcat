## Verified findings (checkpoint 2 — native data plane, updater, service basics)

Legend: **H** high, **M** medium, **L** low. "Prior audit" = the untracked
`AUDIT_REPORT.md` (2026-09-05) recovered from local `refs/t3` checkpoints;
items marked OPEN are still present in today's code.

### Native engine (Go)

- **M (downgraded from H after live test) — TUN reader cannot be stopped; `Stop()` silently leaks it.**
  `TailcatVpnService.kt:265` uses `setBlocking(true)`; `bridge.go:130-135`
  dups the fd and wraps it with `os.NewFile`, which does not register a
  blocking fd with the netpoller. `bridge.go:394` `tunFile.Close()` therefore
  does not interrupt `readLoop`'s `Read` (verified with a blocking pipe:
  Read still blocked 1.5 s after Close; with `O_NONBLOCK` it returns
  `file already closed`). `Stop()` then waits the full 3 s and returns an error
  every caller discards (`_ = bridge.Stop()`). Effects: up to +3 s on each
  `detachTun` in the two-phase start, a leaked goroutine/OS thread/kernel fd
  reference per attach, the dup keeps the old TUN interface alive after Kotlin
  closes its PFD, and the next packet on that interface is eaten by a dead
  bridge. *(Correction from reviewer 1: the tests pass `r.Fd()`, which switches
  the pipe to blocking mode, so they DO hit this bug. `TestLifecycleHappyPath…`
  and `TestDetachTunKeepsPreparedClient` take ~6.05 s each (two 3 s timeouts)
  but never assert latency. Adding a `< 500 ms` assertion there is the
  regression test.)*
  Fix: `syscall.SetNonblock(dupFD, true)` before `os.NewFile` (or
  `setBlocking(false)`), then drop the EAGAIN 1 ms sleep loop
  (`bridge.go:427`); add a test with a blocking fd; log/propagate Stop errors.
  *Live result:* on the emulator the warm→routed detach took ~150 ms (kernel
  IPv6 control packets on a fresh interface wake the blocked reader), so
  startup is not stalled; on **disconnect** Go's dup fd and `tun1` stayed up
  2–3 s after Android closed its fd (traffic blackholed, not leaked). The bug is
  real but timing-dependent; a quiet interface would hit the full 3 s and leak.
- **M — TCP half-close truncates replies (prior audit, OPEN).**
  `netstack_proxy.go:389-392` returns after the *first* copy direction ends and
  the deferred `Close()`s kill the other direction. A client that sends FIN
  after its request (e.g. `nc -N`, some RPC/SMTP/git-style clients) loses the
  response. Fix: wait for both directions (with an idle/linger timeout), as
  upstream `ProxyConns` does; add a response-after-FIN test.
- **M — Per-connection buffers allow memory exhaustion by local apps.**
  `netstack_proxy.go:47,372-373` allocates 2 x 256 KiB per TCP connection
  (cap 1024 → ~512 MiB) and `:597,683,700` 64 KiB per UDP direction
  (cap 1024 flows → ~128 MiB). A browser/torrent client can push the VPN
  process toward an OOM kill (tunnel dies; without lockdown traffic then goes
  direct). Fix: `sync.Pool` of 32 KiB buffers, lower caps, per-UID/per-source
  TCP cap like UDP has.
- **M — Local apps see "connected then closed" for unreachable hosts.**
  `netstack_proxy.go:333-349` completes the local TCP handshake
  (`CreateEndpoint`) before the gateway dial result is known, then FIN-closes
  on dial failure. Apps/browsers get empty responses instead of RST/refused,
  and Happy Eyeballs gets wrong signals. Fix: wait for the dial (bounded) and
  `request.Complete(true)` (RST) on failure.
- **M — Local IPv4 ICMP echo replies synthesize reachability.**
  `bridge.go:674-708` answers every `ping` locally (~0 ms) even when the gateway
  is dead. This contradicts safety invariants 4/5 in spirit and misleads
  connectivity checkers. Fix: drop like ICMPv6, or proxy if a gateway API
  exists; at minimum label in UI/docs.
- **M — Network-change injection is dead code (prior audit, OPEN).**
  `main.go:88,181` reads `activeMonitor`, but production only ever assigns
  `nil` (`lifecycle.go:394,423`). `UpdateNetworkState` interface/DNS updates
  never trigger a Magicsock re-evaluation, so Wi-Fi↔cellular roaming relies on
  upstream timers/write failures. AGENTS/handoff wording implies it works.
- **M — TLS pins are leaf-key pins that expire with the cert, and are checked
  against unverified certs.** `tls_pin.go:11-14` / `PinnedHttps.kt:12-15`.
  Pin `ltQ6…` is the SPKI of the *leaf* `cloudflare-dns.com`/`one.one.one.one`
  cert (expires **2026-12-21**); no backup pin for a rotated key. When
  Cloudflare rotates, the IPv6 egress probe (→ `ipv6Egress=false`, IPv6
  fail-closed), the Kotlin IP audit and the speed test break. Also
  `verifyPinnedConnection` scans `cs.PeerCertificates` and `PinnedHttps`
  scans the server-supplied `chain`, not the verified chain — an attacker with
  any CA-trusted cert can append the public pinned cert and pass (prior audit,
  OPEN). Fix: pin the intermediate/root SPKIs (plus backups) and match against
  `VerifiedChains` / `X509TrustManagerExtensions.checkServerTrusted` output.
- **L — Dead/stale code.** `ipv6DialTimeout` (unused),
  `dialTimeoutFor` (no-op: `_ = dst; return v4Timeout`), `sampleGatewayPing`
  (no-op called every 5 s), `netstackMTU` (only a fallback), `pingFails`
  (write-only in prod), `buildIPv4UDPPacket`/`buildIPv6UDPPacket` (test-only
  helpers in `bridge.go`), `recoverLikeProduction` special-case in the
  production `panicSite`, `ipv4Checksum` duplicating `checksum`. The
  "250 ms IPv6 dial timeout" in AGENTS.md/handoff is no longer true (public
  IPv6 is now rejected pre-dial when `ipv6Egress=false`, otherwise the full
  15 s/10 s budget applies).
- **L — Byte accounting double-counts UDP (prior audit, OPEN).** TUN packets
  are counted in `readLoop`/`writeLoop` (`bridge.go:441`,
  `netstack_proxy.go:232`) and UDP payloads again in `runUDPFlow`
  (`netstack_proxy.go:690,707`); local ICMP/PTB replies count as rx.
  `TxBytes/RxBytes/Wireguard*Bytes` are always 0 in JSON rather than absent.
- **L — `main.go:24` comment** says the resolver falls back to 8.8.8.8/1.1.1.1;
  the code only uses Android-supplied DNS servers. DERP hostnames are therefore
  resolved by the physical network's resolver (expected for a Tailscale client,
  but worth one line in PRIVACY_POLICY).
- **L — `bridge.go:377` `time.Sleep(20ms)`** heuristic for readiness.
- **L — gomobile boundary has no panic recovery.** Exported `Prepare`,
  `AttachTun`, `UpdateNetworkState`, `MeasureTunnel*` call into upstream code
  without `recover()`; any panic there kills the app process (pumps/flows do
  recover).

### Android updater (Settings > Updates)

- **M — SHA-256 verification never runs, but docs/release notes say it does.**
  `SettingsViewModel.kt` calls `downloader.download(asset, expectedSha256 =
  null)`; `ReleaseAsset` never parses GitHub's `digest` field and no
  `SHA256SUMS` asset is fetched. `handoff.md:10` and 1.4.0 notes claim
  "SHA-256 verify when a digest is available". Real protection comes only from
  Android refusing an APK signed by a different key.
- **H (supply chain) — Update trust = GitHub account + the dev machine's
  debug keystore.** The `development` build type (`app/build.gradle.kts`)
  signs with `signingConfigs.debug` (`~/.android/debug.keystore`, well-known
  password). Confirmed: the published v1.4.0 APK is debug-signed (see checkpoint 3), so anyone who obtains that keystore *and* can publish
  a release can push code to every user through the in-app updater. Fix: a
  dedicated release key kept offline; enforce `hasSigningCertificate` against
  a pinned cert digest compiled into the app; publish a signed checksum file
  and verify it.
- **L —** `signatureMismatchReason` returns "OK" whenever comparison fails
  (fine because PackageInstaller enforces, but misleading); uses API-28 flag on
  API 26–27 (lint `InlinedApi`); no size cap; `apkAssetForAbi` falls back to
  any `*.apk` containing the ABI string; `-rc` versions sort as newer than the
  final release; old APKs in `cache/updates` are never deleted;
  `browser_download_url` host is not checked.

### Android VPN service / controller

- **H (availability, leak without lockdown) — Always-on start is rejected
  before the network validates.** *(Confirmed live on API 35: on a working but
  never-validated network the always-on VPN never starts.)* `TailcatVpnService.onStartCommand` →
  `TunnelController.validateStartRequest` requires
  `networkMonitor.isOnline`, which needs `NET_CAPABILITY_VALIDATED`
  (`NetworkMonitor.kt:getCurrentNetworkType`). At boot or on a captive portal
  the always-on start is rejected, `vpnWanted` is cleared, and nothing retries:
  with lockdown the user is offline until they open the app; without lockdown
  traffic goes direct silently. The same check also runs *before* the
  "already running" guard (`:44-52`), so a redundant start intent during a
  roam/unvalidated moment tears down a healthy session via `rejectStart →
  shutdown()`. Fix: don't require VALIDATED to start; move the running-guard
  first; let the engine retry the handshake.
- **M — Native bridge is reflection-only and silently no-ops.**
  `TunnelEngine.kt` resolves every Go call by case-insensitive name at runtime;
  `stop`, `detachTun`, `disarmPumps`, `setSocketProtector`,
  `ensureTransportProtect`, `updateNetworkState` just `return` if missing
  (`updateNetworkState` also swallows all errors). A renamed Go export would
  compile and ship with no socket protection or no stop. The AAR is always
  bundled, so call `com.tailcat.vpn.engine.Engine` directly behind the
  existing `NativeEngine` interface and delete the reflection + `engine.Engine`
  fallback name.
- **M — Capability negotiation is ceremony.** Go hardcodes every capability
  `true` (`main.go:GetCapabilitiesJSON`); Kotlin parses 13 flags, rejects
  unknown keys and builds a "missing" list that can never be non-empty. Since
  both halves ship in one APK, replace with a single `apiVersion` equality
  check (or compile-time binding) and move the "test routing" label to a
  build constant.
- **M — "The app UID bypasses the VPN" is false everywhere it is stated.**
  Self-exclusion was removed (commit `cdb0245`); nothing calls
  `addDisallowedApplication(packageName)`. Stale in AGENTS.md invariant 9,
  `IpAuditor.kt:11` KDoc, `PRIVACY_POLICY.md:56`, `handoff.md:181,193,574`
  (prior audit, OPEN). Consequence: while routes are up the app's own HTTP
  (IP audit, GitHub update check, non-CONNECTED speed test in
  DEGRADED/RECONNECTING) goes through the tunnel, and any app socket open
  during `protectOpenTransportSockets` sweeps is permanently protected
  (bypasses). Speed-test "direct" labelling can be wrong.
- **L — `RECONNECTING` flickers away in ≤1 s**: the polling loop
  (`TunnelController.kt:211-217`) overwrites it with CONNECTED/DEGRADED on
  the next healthy poll.
- **L — Service instance hygiene:** `serviceScope` is never cancelled in
  `onDestroy`; `shutdown()` posts `stopSelf()` which can stop a start that
  arrived in between (the new start resets `shuttingDown`, then `onDestroy`
  tears it down).
- **L —** `EncryptedSharedPreferences`/`MasterKey` are deprecated; a Keystore
  failure in `Application.onCreate` crash-loops the app with no recovery path.
  `ProfileRepository.loadProfiles` drops *all* profiles if one entry is
  corrupt, and the next save persists that loss.

## Verified findings (checkpoint 3 — signing, provenance, parity, UI, docs)

### Release signing and supply chain

- **H — The public v1.4.0 release is signed with the Android debug key.**
  `OpenTailcat-1.4.0-arm64-v8a.apk` (GitHub release, *not* marked
  pre-release) verifies with signer `CN=Android Debug, O=Android, C=US`,
  SHA-256 `dd767011…afa8d6`, which is exactly this Mac's
  `~/.android/debug.keystore` (password `android`). Violates AGENTS/handoff
  invariant 8. Combined with the in-app updater, whoever gets that keystore
  file plus the ability to publish a GitHub release can ship code to every
  install. Every existing user is now locked to that key, so moving to a real
  key needs APK Signature Scheme v3 key rotation (`apksigner rotate` lineage
  debug → release) or users must reinstall. Also publishing a non-prerelease
  GitHub release contradicts "Do not publish or sign it as a VPN release".
- **M — CI does not rebuild the AAR.** `ci.yml` checks `sha256(aar)` against
  the sidecar and that the committed sourcehash matches the tree, but never
  proves the AAR was *built* from that tree (prior audit, partially OPEN).
  Today's tree does match its sourcehash (`1916945b…`, verified).
- **L — Sourcehash depends on locale.** `build-aar.sh:101` and `ci.yml` use
  `sort -z` without `LC_ALL=C`; under `en_US.UTF-8` the hash is `8b85c917…`
  instead of `1916945b…`. Prefix both with `LC_ALL=C`.
- **L — CI hygiene:** actions pinned to tags not SHAs; no `permissions:`
  block; no Gradle wrapper validation; no `gofmt`/staticcheck/govulncheck;
  `assembleRelease`/`bundleRelease` (AGENTS verification list) not run; many
  Dependabot PRs open (Kotlin 2.2.10 → 2.4.20, AGP, Gradle 9.7.1, Compose
  BOM, actions v7). The working tree's uncommitted AGP 9.4.1 / Gradle 9.6.0
  bump builds and passes unit tests + lint, but AGENTS.md still says 9.3.0/9.5.0.
- **L — Test-only code in the shipped library.** `phase8_pcap.go` (pcap
  analyzer) has no build tag and links into `libgojni.so`; move it to its own
  package (e.g. `core-engine/phase8`) used by `cmd/phase8-analyze`.
- **L — ProGuard:** `-keep class com.tailcat.vpn.core.model.** { *; }` and the
  `TailcatVpnService` keep are unnecessary (no reflection on models; manifest
  classes are kept automatically); `-keep class engine.**` is a stale name.
  After removing reflection (see service section), keep only `go.**` and
  `com.tailcat.vpn.engine.**`.

### Token parsing (Kotlin vs Go)

- **M (design) — Two independent strict CBOR token parsers.** `TokenParser.kt`
  (887 lines; `parse()` alone is ~430 lines) duplicates `token.go` +
  `cbor_strict.go`. Divergences from the prior audit are still OPEN:
  region id `4294967297` is silently truncated to `1` by `Long.toInt()`
  (`TokenParser.kt:618`); a non-list `N` or non-string `c` is ignored instead
  of rejected (`:628`); `::ffff:127.0.0.1` / `::ffff:169.254.169.254` pass
  because Java turns IPv4-mapped literals into `Inet4Address` and
  `literalIp` discards them (`:719-731`). Go rejects all of these, so native
  validation prevents a bad connect; Kotlin just gives wrong early UX. The AAR
  already exports `parseToken() -> ParsedToken`: call it from Kotlin (behind an
  interface with a JVM fake for unit tests) and delete the Kotlin parser, its
  parity fixtures and the whole parity bug class.

### UI / app

- **M — Token entry dialog is not screenshot-protected.** `HomeScreen.kt:121-131`

- **M — Profile shown ≠ session running (prior audit, OPEN).**

## Reviewer reports (sequential agents, persisted as they ran)

Detailed findings live in `docs/review-work/`; the main items are merged below.

### 01 — Go engine internals (`docs/review-work/01-go-engine.md`, COMPLETE: 0 H, 4 M, 17 L)

- **M — `Stop()` has no overall bound** (`lifecycle.go:392-435`, `bridge.go:385-409`,
  `netstack_proxy.go:759-797`): two sequential 3 s waits, then an unbounded
  upstream `client.Close()`; concurrent `Stop`/`Prepare` wait on `stopWait` with
  no timeout; Kotlin `onDestroy → shutdown()` calls native `stop()` on the
  **main thread** (3–6 s+ UI freeze on system-initiated destroy). AGENTS'
  "3 s bound" is false.
- **M — `build-aar.sh` writes the sourcehash before building** (`:92-106` vs
  gomobile at `:122`): a failed build leaves the new sourcehash next to the old
  AAR, and both CI checks still pass. It also writes the unverified AAR straight
  into `app/libs` before the javap/16 KB checks. Build to a temp path, verify,
  move atomically, and hash last.
- **M — Egress audit retries forever every ~3 s** (`egress.go:61-82`): no backoff
  or cap; permanent for every user once the pinned leaf rotates (2026-12-21) or
  on a gateway that filters 1.1.1.1:443.
- **M — Existing tests already exercise the blocking-fd bug but assert nothing
  about latency** (see correction above).
- **L highlights:** Go's token error code (and legacy RegionID) depends on map
  iteration order (verified 178/22 split), so Kotlin/Go parity only holds for

### 05 — Go data plane, second opinion (`docs/review-work/05-go-dataplane.md`, COMPLETE: 5 M, 8 L)

- **M (H with a resolver without DoT) — The "per-source" UDP cap is really one
  device-wide cap of 128 flows per address family** (`netstack_proxy.go:41-42,432-447`):
  every app shares the single TUN source address, and answered flows keep their
  slot for 30–40 s (freed only by idle GC). Unit test: query 129 onward gets ICMP
  port-unreachable. **Live:** a burst of 150 DNS queries left all plain UDP
  unanswered for ~20 s; system DNS survived only because Android used DoT to
  1.1.1.1. With a non-DoT resolver or Private DNS off, **all DNS on the device
  goes down** while the UI shows CONNECTED. Fix: key limits per flow/port,
  raise the total cap, close DNS flows right after the reply (or ~5 s idle),
  evict the oldest idle flow instead of refusing.
- **M — UDP payloads of 1233–1472 B are silently lost in the tunnel**
  (`runUDPFlow`; upstream `MaxUDPPayload = 1232`). **Live:** 1232 B got replies,
  1236 B+ got none; Chrome's 1250 B QUIC Initial was retransmitted 5× unanswered,
  so **every IPv4 QUIC handshake fails** and falls back to TCP. Fix: drop and
  count datagrams > 1232 B and synthesize ICMP Frag-Needed (next-hop MTU 1260) /
  Packet-Too-Big (1280) so PMTU discovery adapts; add a test.
- **M — An IPv6 DNS server on a gateway without IPv6 WAN blacks out all DNS**:
  the IPv6 fail-closed gate runs on the *original* destination before
  `resolveDNSDestination` (`netstack_proxy.go:286-293,412-418,464`), so even
  FORCED_RESOLVER=1.1.1.1 can't rescue it. Kotlin accepts IPv6 `customDns`.
  Fix: resolve first, gate the resolved address, and refuse/warn at connect
  when the resolver is IPv6 and `ipv6Egress=false`.
- **M — Correction to the fake-connect fix:** `Client.DialTCP` succeeds as soon as
  the *tunnel* handshake to the gateway completes; the gateway (upstream
  tailscale netstack + Tailcat exit-node handler) dials the real destination
  afterwards and FIN-closes on failure. So "wait for the dial, then RST" can't
  detect unreachable hosts on the client alone, and the
  `"proxy destination not permitted"` string match is dead. A real fix needs a
  gateway change (dial first, then complete the handshake or RST).
- **M — Correction to the memory finding:** gVisor socket buffers dominate
  (local stack 1 MiB send / up to 4 MiB receive; the Tailcat-side netstack up to
  8 MiB RX / 6 MiB TX per connection), not the 256 KiB copy buffers. Set the
  TCP buffer-size range options (e.g. 64 KiB default / 1 MiB max) on the local
  stack, lower `tcpMaxEstablished`, and consider an aggregate memory budget.
- **L highlights:** large pings always fail locally (100% loss above the MTU);
  UDP behaves like a symmetric NAT with a 30 s idle timeout versus the
  gateway's 2 min; `tcpOnly` is decided by a DNS-only probe and never switches
  back on; several telemetry counters count the wrong thing ("DNS queries",
  drop counters, sub-ms RTT); DNS-over-TCP dials once per query and leaks a
  goroutine for ~11 s each; a rare race in TCP accept could crash the app; the
  Frag-Needed/PTB builders have RFC gaps if reused; NAT64 addresses are refused
  although the gateway would carry them over IPv4.
- **Gateway note (not an engine bug):** this gateway drops UDP/53 queries
  larger than 512 B and truncates large answers (TC=1 at EDNS 1232); TCP/53
  retries work. Tell the gateway owner.
- **OK:** 120 s packet-handling fuzz (~610k inputs) found no panics; UDP slot
  accounting balances on every error path; buffer ownership is correct; the
  shared stats fields are locked.

## Is it safe to use if the token is trusted?

Short answer: **reasonable for personal use with Always-on + "Block
connections without VPN" enabled; not something to hand to others yet.**

What is solid: application flows really do go through `Client.DialTCP` /
`DialUDP` (no ordinary socket substitution), routes are installed only after
a live handshake, IPv6 is routed (`::/0`) and fails closed, DNS is steered,
preferences are encrypted, the service surface is locked down, and the failure
paths the prior audit found (H1–H7) were genuinely fixed and tested.

What stops a clean "yes":

1. **Supply chain**: the in-app updater + debug-key-signed releases make the
   developer's laptop keystore and GitHub account the real root of trust.
2. **Leak-on-failure depends on lockdown**: at boot/captive portal the
   always-on start is rejected and never retried; an OOM kill from
   buffer-heavy local traffic is plausible. Without lockdown either case
   silently sends traffic direct. With lockdown it fails closed (no network).
3. **Availability bugs that look like "the internet is broken" while the app
   says CONNECTED**: a burst of more than ~128 UDP flows (DNS lookups, QUIC)
   blocks all UDP, including DNS, for up to 40 s; every IPv4 QUIC handshake
   silently fails because 1250 B datagrams exceed the tunnel's 1232 B limit; an
   IPv6 DNS server kills all DNS on a gateway without IPv6; a dead gateway shows
   DEGRADED forever; engine failures tear the VPN down silently with no retry.
   None of these leak traffic, but they make the app hard to trust day to day.
4. **Operational rough edges**: half-close truncation, fake connect/ping
   semantics, leaf-key TLS pins expiring 2026-12-21, roaming notifications not
   wired to Magicsock, a lock-screen Disconnect button that needs no
   authentication.
5. Phase 8 physical uplink leak capture has still not been done, and the
   current analyzer/recipe could not prove it anyway (no positive control;
   captures the Mac's `en0`; `adb shell` probes are exempt from lockdown).

## What I think of the app

It is an unusually careful prototype. The project writes down its safety
invariants, fails closed by default, and keeps an honest list of what isn't
proven. The Go data plane is well structured around gVisor with bounded flow
tables, per-flow panic isolation and a documented state machine. Most of the
remaining problems are the cost of iterating quickly with several AI agents:
layers that no longer do anything (the capability handshake, the reflection
bridge, the no-op timeout helpers, the two-phase warm TUN), docs that drifted
from the code, and a few real bugs that only show up on a device (blocking-fd
Close, half-close). The biggest wins now come from **deleting code** (the
Kotlin parser, the reflection layer, capability ceremony, dead helpers,
repeated docs) and **fixing signing** before anything else ships.

## Fix log — P1 data-plane batch (2026-09-27, branch `worktree-p1-dataplane-fixes`)

Done in source (not released). Every new test below was checked against a

- **P1-7a UDP flow table** — the per-source-IP cap (128) is gone: all apps share
  the TUN address, so it was a device-wide cap. There is now one table of 1024
  flows; when it is full, the least recently active flow is evicted
  (`dropCounters.udpEvictions`, additive in schema v2) instead of refusing the
  new flow with ICMP port-unreachable. Idle timeouts follow conntrack: DNS 2 s
  after every query is answered, 10 s with one outstanding; other flows 30 s

- **P1-7b UDP over 1232 B** — an unfragmented datagram whose payload exceeds
  `tailcat.MaxUDPPayload` is dropped and counted in `mtuExceeded`, and the app
  gets ICMP Fragmentation Needed with next-hop MTU 1260 (IPv4, DF set only) or
  Packet Too Big 1280 (IPv6). With DF set, the kernel caches the PMTU and returns
  EMSGSIZE, so QUIC stacks shrink their packets or fall back to TCP at once
  instead of retransmitting into the tunnel. Datagrams reassembled from

### Second commit: session failures reconnect (P1-13a/13b/13c)

- **P1-13a engine failures** — a mid-session failure (native FAILED, 3 stale
  health polls, 3 failed stats reads) no longer calls `stopTunnel()`, which had
  cleared `vpnWanted` and removed the notification without a word. The
  controller reports the cause and hands off to a handler that the service
  registers for its session. The service closes the TUN, stops the engine, and
  reconnects through the existing `startWithRetry` backoff while `vpnWanted`
  stays set. The RECONNECTING notification shows the cause, and Disconnect
  still ends it. `MAX_TELEMETRY_FAILURES` went from 1 to 3. If the failure lands
  while the start that connected the session is still returning, the reconnect
  runs after that start instead of being dropped.
  **Not done:** a fail-closed TUN between attempts. Prepare cannot run behind
  default routes, because Tailcat's `createEngine` calls
  `netns.SetEnabled(false)`, which leaves prepare's sockets unprotected. Without
  lockdown, traffic uses the device network between attempts, as it already
  did before this change.
- **P1-13b gateway loss** — Go exports `lastDiscoOkUnixSec`: the bridge start,
  then each successful DiscoPing. `EngineHealth` reports `GatewayLost` when
  `discoStale` is set and the gateway has not replied for 60 s (about 12 failed

  trip it). This triggers the same reconnect, so a dead gateway no longer sits
  in DEGRADED forever, and a path broken by a roam is re-prepared. Engines that
  do not report the field keep the old behavior. Tests:
  `TestLastDiscoOkAdvancesOnlyOnGatewayReply`, three new `EngineHealthTest`

- **P1-13c CONNECTED promotion** — `resyncFromEngine` is now `onUiResumed`,
