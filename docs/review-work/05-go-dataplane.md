- **[M] (H with a non-DoT resolver) [availability/flow-mgmt] core-engine/netstack_proxy.go:41-42,432-447,40,721-748 + VpnInterfaceSpec.kt:4-7 — The "per-source" UDP cap is really a device-wide cap of 128 flows per address family, and answered flows hold their slot for 30-40 s (confirmed live)**
  Every Android app shares the single TUN source address (`100.64.0.2`, `fd7a:115c:a1e0::2`), so `udpActivePerSource[srcAP.Addr()]` is one bucket per IP family. `maxActiveUDPFlowsTotal=1024` can't be reached (the existing `TestBehavioralFlowLimitsAndBackpressure` only passes because it invents 8 source IPs). A flow is freed only by the idle GC (`udpIdleTimeout` 30 s, 10 s ticker), never when the DNS answer comes back. Each resolver lookup and each QUIC connection uses a fresh source port, so it costs one slot for 30-40 s.
  Verified in /tmp/otc-r5 (`r5_udpcap_test.go`): 140 DNS-style queries from `100.64.0.2` with fresh ports, each answered at once. Queries 1-128 were answered. **Query 129 onward got ICMP port-unreachable** (`queueExhaustion=12`, `activePerSource=128` with no flow doing any work). Effect: a burst of more than about 128 UDP flows in ~35 s (a heavy page load with many uncached hostnames plus QUIC, a DNS-heavy app, or any unprivileged app on purpose) blocks all UDP, **including every DNS lookup on the device**, for up to 40 s. Meanwhile the UI shows CONNECTED.
  **Live (emulator, CONNECTED):** one shell burst of 150 `nc -u` DNS queries (fresh source ports) to 1.1.1.1:53, then a fresh raw UDP query every ~3 s. **Every raw UDP query got no answer from t+5 s to t+19 s** and recovered at t+22 s (an earlier 160-query burst left 158/160 unanswered). System (netd) name resolution kept working during the outage only because Android's opportunistic Private DNS reached 1.1.1.1 over DoT (TCP/853). With a profile resolver that has no DoT, or with Private DNS off, system DNS goes down too. All other UDP (QUIC, VoIP, games, apps' own DNS) is refused either way. Rated M in the default setup, H for non-DoT resolvers. Note: the baseline's suggested "per-source TCP cap like UDP has" would have the same single-address flaw.
  Fix: key the limit per (src port) or per destination rather than per source IP, and raise the total cap. Close port-53 flows right after the reply (or give them a ~5 s idle timeout, as conntrack does for unreplied/DNS). Evict the oldest idle flow instead of refusing when the table is full. Add a test that uses the real single TUN address. Effort S-M.

- **[M] [UDP/MTU] core-engine/netstack_proxy.go:681-694 (runUDPFlow) + bridge.go:453 — UDP datagrams with 1233..1472 B payloads fit the TUN MTU but are silently lost in the Tailcat tunnel (confirmed live)**
  Upstream says datagrams larger than `tailcat.MaxUDPPayload = 1232` "are not guaranteed to reach the peer" (third_party/tailcat/tailcat.go:529-533; the WireGuard tunnel is IPv6 with MTU 1280). The engine only checks `len(pkt) > b.mtu` at the IP layer. At the default TUN MTU of 1280, an IPv4 app can send up to 1252 B of UDP payload (up to 1472 B at a profile MTU of 1500), and `runUDPFlow` forwards it with no feedback and no counter. **Live (emulator, CONNECTED, uid 2000 via tun1):** STUN binding requests to `stun.cloudflare.com:3478` padded with an optional attribute got a reply at 100/500/1000/1200/**1232** B and **no reply at 1236/1252/1400/1472 B**. From the host (direct) every size up to 1472 was answered. Consequence: any app sending full-size datagrams under the MTU blackholes. Examples are QUIC: **live tcpdump on tun1 while Chrome opened youtube.com showed `100.64.0.2.41041 > 74.125.197.95.443: UDP, length 1250` sent 5 times over 4 s with no reply at all**. Every Chromium/Cronet QUIC handshake over IPv4 is blackholed, and Chrome falls back to TCP and marks QUIC broken, plus WireGuard/OpenVPN-over-VPN at default MTUs and some games/VoIP. No ICMP comes back, so PMTU discovery can't converge.
  Fix: in `runUDPFlow`, when `n > 1232`, drop the datagram, count it (for example `mtuExceeded`), and synthesize an ICMP Frag-Needed (IPv4, next-hop MTU 1260) or a Packet-Too-Big (IPv6, MTU 1280) toward the app. The kernel then caches the PMTU and DF-setting stacks (QUIC DPLPMTUD) adapt. Alternatively, get upstream IPv6 fragmentation for DialUDP. Add a test with a 1250 B IPv4 datagram. Effort S-M.
- **Note (live, gateway-side, not an engine bug)** — through this gateway, UDP/53 queries larger than **512 B are dropped** (512 answered, 513 not; STUN on :3478 is fine up to 1232). Answers from 1.1.1.1, 8.8.8.8 and 9.9.9.9 to a 4096-EDNS TXT query come back as 43 B **TC=1** (EDNS size 1232), while the host gets 2649/3423 B. Relay to the gateway owner; any engine-side DNS work must not assume a >512 B query path.

- **[L] [ICMP] EXTENDS: "Local IPv4 ICMP echo replies synthesize reachability" — fragmented echo requests get bogus replies, so large pings always fail (confirmed live)**
  `handleICMPv4` (bridge.go:674-708) never looks at MF or the fragment offset. The first fragment of a large echo request is "answered" with a copy of that fragment (MF still set, ICMP checksum computed over the fragment only), so the kernel can never reassemble it. Any non-first fragment of an ICMP datagram whose first data byte happens to be `8` is also rewritten and echoed. Live: `ping -s 1000 203.0.113.1` (unroutable) gets 2/2 replies at 0.1-1.9 ms, while `ping -s 1300` and `-s 3000` get **100% loss**. So ping results depend on packet size, not on reachability. The baseline's fix (drop IPv4 echo like ICMPv6) removes this too. If echo is kept, at least drop fragments (`flags&MF != 0 || offset != 0`) and validate IHL/total length. Effort S.
- **[M] [TCP semantics] EXTENDS: "Local apps see 'connected then closed' for unreachable hosts" — the baseline's fix can't work, because `Client.DialTCP` succeeds before the gateway dials anything; the policy-rejection string match is dead**
  At the gateway, tailscale netstack's `acceptTCP` calls `GetTCPHandlerForFlow` → `getConnOrReset()` (`CreateEndpoint` + `Complete(false)`, which completes the tunnel handshake) and only then runs the handler (tailscale.com/wgengine/netstack/netstack.go:1594-1689). Tailcat's exit-node handler then does `net.Dial("tcp", dst)` and on failure just `c.Close()`s, which is a FIN, not a RST (third_party/tailcat/cmd/tailcat/tailcat.go:1328-1343). The engine's own comments admit this (`lifecycle.go:187-190`, `ipv6_egress.go:12-13`) ("DialTCP ... returns when the tunnel TCP to the gateway is up, before the gateway's remote dial"). So "wait for the dial, then `Complete(true)` on failure" (baseline P1 #6) still reports every unreachable or refused host as connected-then-EOF. The only pre-handshake refusal is a nil gateway handler, which shows up as a bare RST ("connection refused"). The same goes for UDP: `DialUDP` is a local gVisor endpoint with no round trip, so gateway policy drops are silent. As a result `strings.Contains(err.Error(), "proxy destination not permitted")` (netstack_proxy.go:354,525,621) can't match any error these clients return, and `policyRejections` never counts gateway refusals.
  Fix: a real fix needs a gateway change: dial first, then complete the tunnel handshake or RST, as tailscale's own `forwardTCP` does. Until then, document the semantics, delete the string matching, and keep the local handshake gated only on `DialTCP` (which at least catches a dead tunnel or a gateway RST). Effort S client side; M with a gateway change.
- **[L] [UDP semantics] core-engine/netstack_proxy.go:40,420-424,721-748 + tailcat.go:535-537,2185-2190 — The UDP proxy acts like a symmetric NAT with a 30 s mapping timeout (RFC 4787 REQ-5 asks for at least 2 min); server-initiated packets after 30 s of silence are lost**
  Each (src,dst) pair gets its own connected `Client.DialUDP`, which binds a new ephemeral port in the Tailcat netstack (`DialContextUDPWithBind(ctx, lb.addr, dst)`). The gateway therefore sees, and NATs, every destination separately: address-and-port-dependent mapping, so STUN-derived candidates are useless to peers and WebRTC/P2P falls back to TURN. The GC closes a flow after 30-40 s without traffic, but the gateway keeps its side for `DefaultUDPIdleTimeout = 2 min`. The next outbound datagram opens a *new* gateway flow with a new public port, and anything the remote sends to the old port in between hits a client port with no endpoint and is dropped (SIP registrations with 60 s keepalives miss incoming calls; DTLS/ICE pairs break). (Live STUN remapping could not be isolated because the lab's WARP egress remaps on every request anyway.)
  Fix: use about 120 s idle for flows that have seen replies, 5-30 s for unreplied and DNS flows (which also eases the flow-cap finding). Document the per-destination mapping, or ask upstream for an unconnected `PacketConn` API. Effort S (timeouts); L (API).
- **[L] [capability detection] core-engine/main.go:346-366, bridge.go:778-782,825-839 — `tcpOnly` is decided by a DNS query only, and it can only be cleared, never set again**
  `SupportsUDP` sends one DNS query for `a.` to `1.1.1.1:53`. The live gateway handles port 53 specially (see the gateway note above: 512 B query cap, EDNS rewritten to 1232), so the probe measures the gateway's DNS path, not generic UDP forwarding. A gateway that answers DNS but doesn't forward other UDP gets `tcpOnly=false`, and every non-DNS UDP flow blackholes silently (`DialUDP` has no round trip, see the DialTCP finding). - **[M] [memory] EXTENDS: "Per-connection buffers allow memory exhaustion by local apps" — gVisor socket buffers, not the 256 KiB copy buffers, dominate; the proposed 32 KiB pool fix barely moves the bound**
  From source: the local stack keeps gVisor's TCP defaults (send 1 MiB; receive 1 MiB auto-tuned up to 4 MiB, gvisor tcp/protocol.go:41-52,574-586; `tcp.NewForwarder(..., 0, ...)` uses a 1 MiB window). The Tailcat-side netstack that `DialTCP` returns sets RX up to **8 MiB** and TX up to **6 MiB** per connection (tailscale.com wgengine/netstack/netstack_tcpbuf_default.go:14-19). When a local app stops reading, `io.CopyBuffer(local, remote)` blocks once the 1 MiB local send buffer is full, and the gateway's data then piles up in the Tailcat RX buffer, up to its auto-tuned window. So one connection can pin roughly 1 MiB + 256 KiB + up to 8 MiB (the upload direction is similar: up to 4 MiB + 256 KiB + up to 6 MiB), against 512 KiB for the copy buffers alone. The 1024-connection cap therefore bounds memory only in the multi-GiB range. UDP flows use gVisor's 212 KiB stack-default receive buffer on each side plus the 2 x 64 KiB copy buffers. (Estimate from source; not measured on device.)
  Fix: set `TCPReceiveBufferSizeRangeOption`/`TCPSendBufferSizeRangeOption` (for example 64 KiB default / 1 MiB max) and a smaller `ReceiveBufferSizeOption` on the local stack. Lower `tcpMaxEstablished`. Consider an aggregate memory budget, since per-source limits can't work with one TUN address. Effort S-M.

- **[L] [DNS-over-TCP path] core-engine/netstack_proxy.go:589-667 — The tcpOnly DNS path dials once per query, handles queries one at a time, leaks an 11 s timer goroutine per query, and returns oversized UDP answers**
  `exchangeDNSOverTCP` opens a new gateway TCP connection for every query (a full tunnel handshake plus the gateway's own dial) and `runDNSOverTCPFlow` processes one datagram at a time, so a second query on the same socket waits behind the first (up to 15 s dial + 10 s I/O). Each call spawns `go func(){ select{ case <-ctx.Done(): ...; case <-time.After(time.Until(deadline)+time.Second): } }()` with no done channel, so the goroutine and timer live about 11 s after the exchange finishes (1000 lookups/10 s means about 1000 parked goroutines). `if int(ln) > maxUDPPacketSize` can't be true (`ln` is uint16, the max is 65535). The TCP answer (up to 64 KiB) is written back as one UDP datagram with no truncation to the client's EDNS size or 512 B and no TC bit. Given the gateway note above, a truncated answer (TC=1) is common; an oversized one can be cut off by a small client buffer. Only active when `tcpOnly` is true, which is why it's rated L.
  Fix: reuse one pipelined TCP connection per resolver (RFC 7766), give the watchdog a `done` channel (or use `context.AfterFunc`), truncate the answer to the query's EDNS size (or 512) and set TC. Effort S-M.
- **[L] [robustness] core-engine/netstack_proxy.go:281-302,759-797; bridge.go:767-775 — Two small panic/crash-surface issues**
  (1) `acceptTCP` runs on a goroutine spawned by gVisor's forwarder with **no recover** (the `recoverFlow` defer only starts inside `proxyTCP`). It calls `p.tcpWg.Add(1)` after an unlocked `p.closed` check, while `Close()` may already be in `tcpWg.Wait()`. That is exactly the "Add concurrently with Wait" misuse the UDP path avoids with `udpMu`, and if it hits, `sync` panics and the whole app process dies. (unverified: the window is only a few instructions inside the last `Done`; found by reading `sync.WaitGroup`.) (2) The RTT sampler goroutine uses `recoverPump("rtt sample")`, so a panic in the non-required `DiscoPing` marks the session FAILED and tears the VPN down. `recoverPumpLogOnly` (used for the egress and UDP-reprobe loops) is the documented intent for non-required loops. - **[L] [latent ICMP builders] core-engine/bridge.go:453-461,588-664 — Frag-Needed / Packet-Too-Big generation is effectively unreachable today, and not RFC-clean if it is reused**
  The kernel never writes a packet larger than the TUN MTU (no vnet header/GSO, and Kotlin/Go MTUs share the 1280-1500 range and are staged before `prepare`), so `len(pkt) > b.mtu` only fires if something is misconfigured. If these builders are reused for the >1232 B UDP fix they need these corrections: Frag-Needed is sent regardless of DF; non-first fragments and ICMP error types 11/12 (only types < 8 are excluded) aren't skipped; there's no rate limit; the PTB can be up to `mtu` (1500) bytes although RFC 4443 §2.4 caps ICMPv6 errors at 1280. Nit: `int(pkt[off+1]+1)*8` / `int(pkt[off+1]+2)*4` in `ipv6FinalNextHeader` do byte arithmetic and wrap at 255/254, but a header that long can't fit in a ≤1500 B packet, so there's no practical effect (the packet is dropped as malformed either way). Effort S.
- **[L] [IPv6 policy edge] core-engine/ipv6_egress.go:56-70, netstack_proxy.go:270-279 — NAT64 destinations are refused although the gateway translates them to IPv4**

### Answers to the brief's specific questions (verified OK unless noted above)

- **UDP reservation/rollback/unregister accounting:** balanced on every path. There are five exits in `acceptUDP` (CreateEndpoint error, DNS policy reject, closed, duplicate key, handoff) plus `dialAndRunUDPFlow`'s `handedOff` guard. `unregisterFlow` decrements exactly once per inserted flow (`unregistered.Swap`) even when a newer flow has replaced the map entry (`cur != flow`: counters are still decremented, the entry is kept). GC `close()` → reader error → `runUDPFlow` defer → `unregisterFlow` is race-free (`closeOnce`, `remoteMu` hand-off in the dial path). A true duplicate live key can't occur, because gVisor delivers packets for a registered 4-tuple to the endpoint and `RegisterTransportEndpoint` fails while the old endpoint is still bound. The counters don't drift; the capacity problem is the single-address bucket above, not a leak. When `acceptUDP` returns false *after* `CreateEndpoint` (policy/duplicate/closed), the packet has already been queued to the new endpoint, which is then closed, and gVisor additionally emits ICMP port-unreachable (nic.go:879-894). `udp.ForwarderRequest` holds a `pkt.Clone()` that nothing ever `DecRef`s. gVisor offers no release API; the Go GC reclaims it, same as in tailscale. Harmless.
- **tcp.NewForwarder:** `HandlePacket` spawns one goroutine per SYN (`go f.handler`) and dedupes by 4-tuple. `maxInFlight=1024` bounds only requests that haven't `Complete()`d yet; `proxyTCP` completes right after the local handshake, so the running total is bounded by `tcpMaxEstablished` (a non-atomic check-then-add, which can overshoot by a few; negligible). Bad-checksum SYNs aren't filtered (`csumValid` is forced true by RX offload).
- **RXChecksumOffload / SetSpoofing / SetPromiscuous:** app packets with bad L4 checksums would be accepted, but only the kernel writes to the TUN (unprivileged apps can't send raw IP), and it always computes full checksums. Accepted as is. Spoofing/promiscuous is what makes the transparent proxy work; multicast/broadcast are still dropped (verified above).
- **PacketBuffer refcounts / buffer reuse:** `inject` → `buffer.MakeWithData` copies (`NewViewWithData` → `v.Write`), so `readLoop`'s reused 64 KiB buffer is safe. `writeLoop`'s `ToView()` copies, and it releases the view and `DecRef`s exactly once. ICMP/PTB builders copy into new slices. `tunWriteMu` serializes all TUN writers.
- **Locks/atomics:** `transport` and `rttMs` are read and written under `rttMu` (not lock-free as the brief suspected). `lastTx/lastRx/lastTime` are touched only by `rateCalcLoop`. `onHealth` is assigned before `Start` (happens-before via goroutine start). `GetStats` isn't a consistent snapshot, which is acceptable for telemetry. The RTT/re-probe goroutines aren't in `b.wg`, but they use `b.ctx` and at most write a stale `healthUnix` that non-RUNNING states ignore.
- **tunnelLookupA / parseDNSA:** fixed ID `0x1111`, and no ID/QR/opcode/question match. Acceptable because it runs over TCP through the trusted gateway. Every read is bounds-checked, the pointer-jump limit is 10, and the length is capped at 4096.
- **speedtest.go parsing:** robust (header parse via `http.ReadResponse`, bounded bodies, deadlines on every read). Minor: `tunnelHTTPRead` counts a final up-to-2 s stalled read in `elapsed`, and its per-read `SetReadDeadline` replaces the context deadline. Ping/upload inflation is already in the baseline.

## Overall assessment (reviewer 5)

**Counts (new findings and EXTENDS only):** H 0 (1 M item becomes H with a non-DoT resolver), M 5, L 8, plus 1 gateway-side note.

- **M:** (1) The "per-source" UDP cap is device-wide (single TUN address), and answered DNS/QUIC flows hold slots 30-40 s. A 150-query burst refused all raw UDP for about 20 s live (H if the resolver has no DoT). (2) An IPv6 DNS server on a gateway without IPv6 WAN blacks out DNS, because the IPv6 gate runs before the DNS redirect (unit test + live ICMPv6 unreachable). (3) UDP payloads above 1232 B are silently lost in the tunnel even though they fit the TUN MTU. Live: 1232 answered, 1236 not; Chrome's 1250 B QUIC Initials go unanswered. (4) EXTENDS fake-connect: `DialTCP` succeeds before the gateway dials, so the baseline's "RST on dial failure" fix can't work, and the policy-string match is dead. (5) EXTENDS memory: gVisor/Tailcat socket buffers (1-8 MiB per connection) dominate the 256 KiB copy buffers.
- **L:** fragmented pings get bogus local replies (live 100% loss above MTU); symmetric-NAT UDP with a 30 s mapping timeout versus the gateway's 2 min; `tcpOnly` probes only port 53 and never re-latches; misleading "DNS queries", drop and sub-ms RTT telemetry; DNS-over-TCP per-query dial, 11 s goroutine and oversized UDP answers; unrecovered `tcpWg.Add` race in `acceptTCP` plus the RTT sampler marking FAILED on panic; latent Frag-Needed/PTB RFC gaps; NAT64 prefix refused without IPv6 egress.

**Top 3 to fix:** (a) Flow table: key UDP limits per port/destination instead of the single TUN IP, give DNS/unreplied flows short timeouts and replied flows ~120 s, and evict instead of refusing. That fixes the device-wide UDP/DNS DoS and the RFC 4787 timeout together. (b) Send an ICMP Frag-Needed/PTB (MTU 1260/1280) for UDP payloads above 1232 so QUIC and other PMTU-aware stacks adapt instead of blackholing. (c) Apply the IPv6-egress gate to the *resolved* DNS destination and refuse or warn on an IPv6 resolver when `ipv6Egress=false`.

**Scope results:** the packet parsers are memory-safe (120 s fuzz of `handleOutboundPacket`, about 610k execs, no panic), UDP accounting is exact on every error path, PacketBuffer/refcount handling and buffer reuse are correct, and shared fields are properly locked.
